# Dump Analysis — DScript / SQL2016 JS scripts

## DScript extension (`!dscript.run`)
- DLL: `C:\Program Files\WindowsApps\Microsoft.WinDbg.Slow_<ver>\amd64\pri\DScript.dll` (ver changes on every WinDbg auto-update).
- **cdb.exe on THIS box is NOT on PATH and NOT in `Windows Kits\...\Debuggers`** — it ships inside the WinDbg Store package: `C:\Program Files\WindowsApps\Microsoft.WinDbg.Slow_<ver>_x64__8wekyb3d8bbwe\amd64\cdb.exe`. Resolve it dynamically: `$cdb = Join-Path (Get-AppxPackage *WinDbg* | Select-Object -First 1).InstallLocation 'amd64\cdb.exe'`. The dump-analysis SKILL 1.1 now includes this — so RUN cdb.exe yourself (Path A), do NOT fall back to hand-off just because Kits paths are empty.
- Run debugger logic through a `create_file`'d `.ps1` invoked with `pwsh -NoProfile -File <script.ps1>` — the persistent pwsh terminal TRUNCATES multiline pastes containing `$var='...(...)...'` (parens), so inline multiline cdb-driver commands fail silently.- Encrypted JS library: `C:\Tools\SQL2016\*.js` AND `C:\Tools\dscript\sql2019\*.js` (task.js, all_ios.js, callstack.js, tsqlstack.js, ...). Decrypted by DScript at runtime — cannot read as text.
- DScript hosts **4 COM objects** (Object Model Root / Tabular Output / Scripting Host / Arguments Collection). cdb refuses `!dscript.run` unless their 4 CLSIDs are registered, else: `*** ERROR: The DSCRIPT extension is not registered as a COM server ... dscript!DebugExtensionInitialize failed with 0x80070005`.
- **PERMANENT FIX (no admin / no UAC) = per-user HKCU registration.** Run:
  `pwsh -NoProfile -File .github\skills\dump-analysis\scripts\register_dscript.ps1`
  It auto-detects the newest `DScript.dll` (running debugger proc → WindowsApps `Microsoft.WinDbg*` pkg → Windows Kits), re-extracts the 4 CLSIDs from the dll's Unicode strings, and writes `HKCU\Software\Classes\CLSID\{guid}\InprocServer32 = <dll>` (ThreadingModel=Both). COM resolves HKCU before HKLM → no elevation.
- The 4 CLSIDs (stable across versions, baked in DScript.dll): `7cadfd15-7ab3-4b69-9a4d-981951734836`, `931a9cec-62c7-4747-b67b-eb9a785aee3d`, `987f2c24-3a5a-49de-a179-1b4a6688169f`, `ff9f7123-876b-467a-b7e9-21df9dc1dedc`.
- **WinDbg auto-update breaks it** (HKCU value points to the OLD package path). Symptom returns: `not registered as a COM server`. Fix = just re-run `register_dscript.ps1` (it re-detects the new path). HKCU keys themselves persist across reboots.
- HKCU registration takes effect in an ALREADY-RUNNING cdb (COM resolves at activation time) — no need to relaunch cdb.
- The OLD HKLM/elevated-cdb method also works but needs UAC and hard-codes one version path → avoid; prefer the HKCU script.
- `!dscript.run` auto-loads DScript (prints `--- Loading DScript`). The explicit `.load "<path with spaces>"` line fails (cdb eats quotes/spaces) but is harmless.
- task.js / tsqlstack.js take **current thread context** — must `~<TID>s` first to target a specific thread.
- **tsqlstack.js works iff the CompPlan/CSQLSource is still ALIVE — NOT simply "no exception".** Judge by the stack:
  - `catch$89` (`CMsqlExecContext::FExecute'::catch$89`, **statement-execution** exception) in early cleanup (e.g. `CXStmtDML::FinishOnException` → `Rollback`): CompPlan still intact → **tsqlstack STILL returns the T-SQL** (proven case 2606250030005483 thread 689 → `UPDATE [Shop] SET session_*...`, @0=15068466).
  - `catch$3` (`CSQLSource::FCompWrapper'::catch$3` → `CCompPlan::~CCompPlan` → `CMetaStmtSet::Cleanup`) = **compile failed, plan being destroyed** → tsqlstack reports **`Null CompPlan` / "not a CSQLSource"** (no text). Same for deep destructors (`CQueryExecContext::~`, freeing query memory).
  - On a **minidump**, even when statement text is retrieved, varchar/large param VALUES may fail with `0x8007001E Cannot read from virtual address` (heap not captured) — statement text still usable, param values partial.
- WinDbgCs DCS Mirrors (`!dcs_initsymsvr sqlservr`) is a SEPARATE, UNRELATED mechanism. **NO DScript `.js` uses it** — do NOT `.load WinDbgCsExt.dll` or run `!dcs_initsymsvr`/`!dcs_initlocal` before ANY `!dscript.run` (task.js, tsqlstack.js, callstack.js, all_ios.js, … there are many .js scripts). Doing so POISONS the session and turns the working run into a clean `0x800A0030 [Error in loading DLL]` failure. Just run `!dscript.run` on a FRESH cdb with the normal symbol path.
- **BYPASS the 404 manifest (per SOP `SQLMirrors0003`, DsMainDev `Sql/Ntdbms/dscript/Docs/CsScripts/SOPs/`):** when `!dcs_initsymsvr` 404s (no published SymSvrManifest for the build, e.g. SQL2019 CU20), load mirrors manually — (1) `lmDvm sqlservr` to get the exact build (e.g. `15.0.4312.2`); (2) copy `SqlDebugTypes.dll` + `SqlCsScripts.dll` + `SqlDebugTypesPartial.cs` from `\\sqlbuilds\released\SQLServer2019\RTM\Hotfixes\<build>\bin\retail\x64\` INTO the dump folder; (3) in a DEDICATED session `.load <full>\WinDbgCsExt.dll` then `!execute <dumpFolder>\SqlCsScripts.dll`. SqlCsScripts.dll is built by `Sql/Ntdbms/dscript/SqlCsScripts/SqlCsScripts.csproj`; the manifest by sibling `SqlCsScripts.SymSvrManifest/` (`SymSvrManifestConfig.xml`: NativeModule=sqlservr.exe, OutputModule=SqlCsScripts.SymSvrManifest.dll, Modules=SqlCsScripts.dll+SqlDebugTypes.dll+CsDebugScript.*).
- **WHY loading WinDbgCsExt breaks `!dscript.run`:** `WinDbgCsExt.dll` (newest at `C:\Tools\WinDbgCs\WinDbgCsExt.dll`, 2025-06-24 build w/ extra `CsDebugScript.Utils.dll`; older `C:\Tools\windbgcs.3.0.8\`) is a DIFFERENT extension — the **CsDebugScript** engine (managed **C#/Roslyn** `Microsoft.CodeAnalysis*.dll` + `CsDebugScript.Engine.dll` + its own `msdia140.dll`), NOT DScript; **a newer build does NOT change any of this.** (a) `!dcs_initsymsvr` pulls managed *mirror* assemblies for the build via a symbol-server manifest (`CsDebugScript.SymSrvManifestGen.exe`); on a build with no published SqlCsScripts manifest → **404** (a newer WinDbgCsExt binary can't fix a missing server-side manifest), and on a minidump the mirrors can't bind to process memory anyway. (c) A bare `.load WinDbgCsExt.dll` also fails unless you give the full `C:\Tools\WinDbgCs\WinDbgCsExt.dll` path / set `.extpath`. - **CORRECTION (2026-07, proven by user's WinDbg GUI on case 2606250030005483): tsqlstack.js does NOT hang — it is just VERY SLOW (~5 min / ~290s per thread).** WinDbg log: `!dscript.run ...tsqlstack.js` → `Completed request (290151 ms) : ... returned S_OK`. - On a minidump the decode still SUCCEEDS but the tail often ends with COM `0x80020101` / `0x8007001E Cannot read from virtual address` — that is just missing param/large-value bytes; **the statement text printed after `Input string:` is already fully captured and usable** (proven case 2606250030005483 thread 132 → refund-record paging `SELECT TOP 100 ... ## Main vs child (parallel) exec-thread classification (proven case 2606250030005483)
- **主线程 (main/top-level request worker) = stack CONTAINS the TDS request-dispatch frames** `process_messages → process_commands_internal → process_request` (→ `CSpecProc::Execute` / `CSQLSource::Execute`). Judge by presence of `process_request`, NOT by the top frame (a parallel-parent can be stopped at `CQueryScan::AbortSubprocsAndWait`/`CXPipe::GetRow` yet still be a main thread because it has `process_request`).
- **子线程 (parallel exchange worker) = NO `process_request`** in the stack; only exchange/producer frames (`FnProducerThread`, `SubprocEntrypoint`, `CXPipe::GetRow`, `CQScanExchange*`, `CBpQScanSort::*`, `GetRowFromProducer`). Child workers carry NO top-level T-SQL text — the statement belongs to their parent main thread. DOP shows up as equal-size clusters (e.g. two groups of 8 = two DOP≈8 queries).
- Classifier `classify_main_child.ps1` (in the case report folder): scans each last `~*k` block in allk.txt; `process_request|process_commands_internal|process_messages` ⇒ main; else parallel-frame + SQL-frame ⇒ child. Case 2606250030005483: 42 main (14 of them `process_request→CSQLSource::Execute` exec threads) + 24 parallel children.
- HTML deliverable pattern: `gen_sql_exec_thread.ps1` reads allk.txt (per-tid last block) + tsqlstack.txt (`===THREAD_<tid>===` markers) → emits `sql_exec_thread.html` with one collapsible `<details><pre>` card per thread (callstack + tsqlstack). Build the whole HTML in a create_file'd `.ps1` (Chinese literals survive) and write with `[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`; NEVER PowerShell here-strings for Chinese (corrupts to ?).
- tsqlstack legend used in report: ✅ 完整 (text+CompPlan alive) / ⚠️ 部分 (text readable but CompPlan Null or param page missing) / ⛔ 无 (not a CSQLSource, or statement body page missing = unrecoverable). The exception-path column (`catch$89` execute-abort vs `catch$3` compile-fail) is orthogonal to whether text was recovered — an aborting `catch$89` thread often STILL yields full T-SQL.

## task.js output fields (per-thread)
- `Worker state`: WORKER_STATE_SUSPENDED = truly stuck; RUNNING/RUNNABLE = not stuck.
- `Wait type description` + `BLOCKERS` section (walks SQL blocker chain). `No blockers were found` + PWAIT_IO_COMPLETION = stuck on async IO, root cause in IO subsystem (not SQL self-deadlock).
- **`SOS_Task` header is the AUTHORITATIVE parent↔child map — group threads by SPID, NOT by call-stack top frame.** Format differs between main and child:
  - MAIN: `SOS_Task : 0x.. (SPID:NNNN, Wrk:0x.., ~TIDs, Sch13:0x.., dbid:N (from diag))` — **has a trailing `dbid:` field**.
  - CHILD (parallel worker): `SOS_Task : 0x.. (SPID:NNNN, Wrk:0x.., ~TIDs, Sch4:0x..)` — **NO `dbid:` field** (and may carry an `ECID:` field). Same SPID as its parent main thread.
  - Parser regex must make dbid OPTIONAL and NOT anchor on `)`: `\(SPID:(\d+),\s*Wrk:\S+,\s*~(\d+)s,\s*Sch\d*:(0x[0-9A-Fa-f]+)(?:,\s*dbid:(\d+))?`. A dbid-mandatory regex silently blanks every child SPID.
  - **Grouping by SPID beats call-stack grouping** (proven case 2606250030005483): a SINGLE parallel query (SPID 1357 = main thread 132) spawned **22 child workers** spread across MULTIPLE exchange operators — so they had DIFFERENT top frames (PWAIT_CXCONSUMER ×18, PWAIT_BATCH_MODE_SORT ×4) yet all share SPID 1357. Do NOT treat distinct top-frame clusters as distinct queries; confirm with SPID. (Also: SPID 1461/main 255 → 2 children; the other 12 exec mains were serial / childless.)
- **Sweep pattern to build the map:** for each exec/parallel TID run `~<TID>s ; .echo ===TASK_<TID> <role>=== ; !dscript.run <task.js>` into one log (`.logopen`/`.logclose`), then parse each `===TASK_<TID>===` block for the SOS_Task SPID and group. task.js is ~seconds/thread in a FRESH cdb, so a 38-thread sweep is cheap.

## task.js per-block field extraction + BLOCKERS parsing (proven case 2606250030005483, runtime-state table)
- Each swept block (`===TASK_<tid> MAIN/CHILD===`) carries these extractable fields (own copy anchored at **column 0**, no leading spaces):
  - `Task state, paramflags: <RUNNING|RUNNABLE|SUSPENDED> ...`
  - `Worker state          : WORKER_STATE_<...>`
  - `Elapsed time          : <N> ms  (0 days hh:mm:ss.fff)` — total task lifetime.
  - `CPU time              : <N> ms`
  - `Task function         : sqllang!process_commands` (main) / `sqlmin!SubprocEntrypoint` (child).
  - `Wait type description : PWAIT_... (0x..)` — **ABSENT when the task is RUNNING** (no current wait). Treat empty ⇒ RUNNING/on-CPU.
- **BLOCKERS section format:**
  - `------ BLOCKERS -----------` then either `No blockers were found`, OR `N blocker(s) found ...` followed by the blocker dump **each line prefixed with `  ---->  `**: `  ---->  ------ BLOCKER_0 -----: <reason>` (e.g. `SEARCH_OR scheduler yield`), then `  ---->  SOS_Task : 0x.. (SPID:NNNN, ..~TIDs..)` = the blocking task, plus `---->`-prefixed duplicates of Task state / Elapsed / CPU / Task function.
  - **PARSER RULE: anchor the task's OWN fields with `^Field` (start-of-line) so you don't accidentally grab the blocker's `  ---->  Field` duplicate.** The blocker's SPID/tid comes from the FIRST `---->\s*SOS_Task ... \(SPID:(\d+),.*~(\d+)s` line; the reason from `BLOCKER_0[^:]*:\s*(.+)`.
- **What the table revealed (root-cause confirmation):** 10 of 14 exec mains (689/591/423/448/523/132/232/418/454/370) were all blocked by **SPID 1346 (~144s)** with reason `SEARCH_OR scheduler yield`, each waiting `PWAIT_SOS_SCHEDULER_YIELD` — while thread 144 itself is `RUNNING`, no wait, monopolizing Sch13 = textbook "Stalled Dispatcher". A per-thread runtime-state table (Task/Worker state · Wait · Elapsed · CPU · Task function · Blocking) makes the "everyone blocked by one culprit" pattern obvious at a glance.
- **PowerShell gotcha (cost a run):** a helper function named `H` (or any single letter that is a built-in alias, e.g. `h`=Get-History, `r`=Invoke-History, `%`=ForEach) is SHADOWED — **alias resolution beats functions** — so `(H $x)` silently calls `Get-History -Id $x` → `Cannot convert "SUSPENDED" to Int64`. Name HTML/util helpers with ≥2 letters (`Enc`, `HtmlEnc`).
